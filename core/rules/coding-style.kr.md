## 코딩 스타일

### 네이밍 컨벤션

- 이름은 의도를 드러낸다. 축약보다 명확함을 우선한다.
- 변수·함수는 camelCase, 클래스·타입은 PascalCase, 상수는 UPPER_SNAKE_CASE를 기본으로 한다. 단, 해당 언어의 관용적 표기가 다르면 그 언어 컨벤션을 따른다.
- DB 스키마(테이블명, 컬럼명)는 언어와 무관하게 snake_case를 따른다. ORM에서 애플리케이션 코드의 필드명이 camelCase라도, 실제 컬럼/테이블명은 snake_case로 매핑한다.
- 불리언 이름은 `is`/`has`/`should` 등으로 시작해서 의미를 명확히 한다.
- 한 글자 변수명은 반복문 인덱스(`i`, `j`)처럼 관용적으로 통용되는 경우에만 허용한다.

### 들여쓰기·공백

- 들여쓰기는 스페이스 2칸을 기본으로 하되, 프로젝트에 기존 컨벤션이 있으면 그것을 따른다.
- 탭과 스페이스를 섞지 않는다.
- 파일 끝에는 개행 한 줄만 남긴다.
- 줄 끝 공백(trailing whitespace)을 남기지 않는다.

### 중괄호·블록 스타일

- 여는 중괄호는 같은 줄에 둔다.
- 한 줄짜리 조건문이라도 중괄호를 생략하지 않는다 — 이후 코드가 추가될 때 버그를 방지한다.
- 중첩은 최대한 얕게 유지한다 (early return으로 중첩 depth를 줄인다).

### 줄 길이

- 한 줄은 100자를 넘기지 않는 것을 권장한다. 하드 제한은 아니며, 가독성을 해치면 줄바꿈한다.
- 긴 함수 호출·메서드 체이닝은 인자·메서드 단위로 줄바꿈한다.

### 주석 스타일

- 주석은 "무엇"이 아니라 "왜"를 설명할 때만 쓴다 — 코드로 표현 가능한 내용은 이름·구조로 드러내고 주석을 달지 않는다.
- 죽은 코드·주석 처리된 코드는 커밋에 남기지 않는다.
- TODO는 담당자나 이슈 링크 없이 남기지 않는다.

### 코드 구조·순서

- 함수는 하나의 일을 한다. 파일이 커지면 책임 단위로 분리한다.
- import·의존성은 외부 라이브러리 → 내부 모듈 순서로 정렬한다.
- 파일 내에서 export되는 주요 함수·클래스는 상단에, 헬퍼 함수는 하단에 배치한다.
- 가능한 한 불변(immutable) 데이터를 선호한다.

### 포매팅 & 자동화

- 프로젝트에 formatter(Prettier, Black 등) 설정이 있으면 그대로 따르고, 수동으로 스타일을 논쟁하지 않는다.
- formatter·linter 설정이 없는 새 프로젝트에서는 해당 언어의 표준 도구 도입을 제안한다.
- 커밋 전 자동 포매팅을 거친다. (가능하면 pre-commit hook으로 강제한다)
